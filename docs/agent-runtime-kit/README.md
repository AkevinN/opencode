# Agent Runtime Kit · AI 编码助手运行时能力规范与提示词包

> **这是什么**：一套**可直接复制到任意项目**的规范（spec）+ 提示词（prompt）+ 验收断言（acceptance），
> 用来在你自己的项目里**从零实现**或**审计优化** AI 对话/Agent 运行时的 17 项核心能力。
>
> **怎么来的**：从 `opencode` 生产代码逐行分析后抽象而成。分析原文在 [`../context-and-streaming/`](../context-and-streaming/)（17 篇，11k 行，256 处带行号的源码引用）。
> 本包是那份分析的**规范化、去具体实现化**版本——只讲「必须满足什么」，不讲「opencode 在哪一行怎么写的」。

---

## 0. 三十秒上手

```bash
# 1. 复制整个工具包到你的项目
cp -r docs/agent-runtime-kit /path/to/your-project/docs/

# 2. 打开你的 AI 编码助手，第一条消息贴这个
cat docs/agent-runtime-kit/prompts/00-orchestrator.md
```

然后按提示词的引导走。**不要一次性把 17 个规范全贴给 AI**——上下文会爆，而且 AI 会做出一堆互相不一致的决定。工具包的整个设计就是为了让你一次只推进一个能力。

## 1. 它解决什么问题

你在做一个带 AI 对话的产品。做到某个阶段会**同时**撞上这些墙：

| 症状 | 对应能力 |
| --- | --- |
| 长会话报 `context_length_exceeded` | SPEC-14 压缩 |
| 改了项目配置，模型还拿着旧的干活 | SPEC-12/13 系统上下文与纪元 |
| 流式输出一长就卡、掉帧 | SPEC-03 客户端同步、SPEC-06 Markdown 管线 |
| 刷新页面对话过程全丢 | SPEC-02 事件与传输 |
| 模型跑着的时候用户没法插话 | SPEC-07 输入编排 |
| 工具输出一次吃掉半个上下文窗口 | SPEC-11 输出治理 |
| 模型乱改文件，或者权限弹窗烦死人 | SPEC-09 权限、SPEC-10 文件安全 |
| 几十篇操作手册没法都塞进 prompt | SPEC-15 技能 |
| 流式时页面乱跳、上滑被强制拉回底部 | SPEC-04 时间线与滚动 |

这些墙**不能靠打补丁绕过去**，每一堵背后都有一个需要正确设计的机制。本包就是这 17 个机制的规范。

### 不是什么

- ❌ 不是一个库/框架。**没有代码可以 `npm install`**，只有规范和提示词。
- ❌ 不绑定任何技术栈。规范用语言无关的伪代码 + TypeScript 接口契约表达。
- ❌ 不替你做产品决策。规范里所有可调参数都标了默认值和调整影响，由你定。
- ❌ 不要求全部实现。能力之间有依赖图，你可以只做前几层。

## 3. 两种用法

### 用法 A · 全新实现（greenfield）

你的项目还没有这些能力，或者只有最朴素的版本。

```
00-orchestrator  →  02-plan  →  [03-implement → 04-verify] × N  →  E2E 验收
```

跳过审计，直接从 `CAPABILITIES.md` 的**推荐实施顺序**挑能力。

### 用法 B · 审计优化（brownfield）

你已经有一套能跑的实现，想知道差在哪、怎么补。

```
00-orchestrator  →  01-audit  →  02-plan  →  [03-implement | 05-optimize → 04-verify] × N
```

`01-audit` 会产出一份差距报告：每项能力标 **缺失 / 部分 / 符合**，每个判定都带 `file:line` 证据。
**审计阶段不允许 AI 提修改方案**——先把现状摸清楚，避免它一边看一边改。

## 4. 五步工作流详解

| 步骤 | 提示词 | 输入 | 输出 | 关键约束 |
| --- | --- | --- | --- | --- |
| ① 定向 | `00-orchestrator.md` | 你的项目 + 目标 | 工作协议 + 路线选择 | 建立「不发明、引用条款号、改动前先问」三条纪律 |
| ② 审计 | `01-audit.md` | 目标代码库 | `audit-report.md` + `audit.json` | 每条判定必须有证据；**不准提方案** |
| ③ 计划 | `02-plan.md` | 差距报告 + 你的约束 | `implementation-plan.md` | 必须尊重依赖图；每个里程碑有进入/退出条件 |
| ④ 实施 | `03-implement.md` | 单个 SPEC id | 代码 + 适配说明 | 最小 diff；跟随宿主项目约定；**加依赖要先问** |
| ⑤ 验证 | `04-verify.md` | 单个 SPEC id | `verify-<spec>.md` + 更新 YAML | 每条断言给通过/失败/不适用 + 证据 |

优化路径用 `05-optimize.md` 替换步骤 ④：它只针对「已实现但偏离规范」的情况，产出**最小修正 diff**，不重写。

## 5. 规范条款的等级约定

每份 SPEC 里的条款都有 ID 和等级：

| 等级 | 含义 | 不满足的后果 |
| --- | --- | --- |
| **必须**（MUST） | 不满足则该能力在真实负载下必然出问题 | 视为未实现 |
| **应该**（SHOULD） | 强烈建议；偏离需要写明理由 | 可接受但要记录 |
| **可以**（MAY） | 可选增强 | 无影响 |

条款 ID 形如 `R-08-03`（SPEC-08 的第 3 条）。验收断言 ID 形如 `A-08-05`。
**提示词要求 AI 在所有产出里引用条款 ID**，这样你能一眼核对它有没有跳步。

> 断言的 `group` 字段沿用分析原文的不变量标记（`T1`、`M4`、`R5`…），可以直接回溯到
> [`../context-and-streaming/`](../context-and-streaming/) 对应章节的同名不变量。

## 6. 关于「可调参数」

规范里凡是带具体数值的地方（超时、阈值、并发度、缓存上限），都在**第 5 节「可配置参数」**里列成表格，格式：

| 参数 | 参考默认值 | 可调范围 | 调大 / 调小的影响 |
| --- | --- | --- | --- |

**这些默认值是 opencode 在真实负载下调出来的，直接抄通常不会错**，但它们不是规范的一部分——
规范约束的是「必须有这个参数」和「参数的语义」，不是具体数字。

## 7. 给 AI 的硬约束（提示词里已内置）

工具包的所有提示词都内置了这几条，你不需要重复交代：

1. **不发明**。规范没写的行为，不要臆测；不确定就停下来问。
2. **引用条款号**。每个设计决定要说明它满足哪条 `R-xx-xx`。
3. **跟随宿主约定**。目录结构、命名、错误处理风格、测试框架，一律跟目标项目走，不要照搬规范里的示例写法。
4. **最小 diff**。不顺手重构无关代码，不升级依赖，不改格式化配置。
5. **加依赖先问**。任何新的 npm/pip 包都要先说明为什么必须、有没有零依赖替代。
6. **产出可验证**。每个能力实施完要能对着 `acceptance/SPEC-xx.yaml` 逐条回答。

## 8. 常见用法问答

**Q：我只想解决「流式卡顿」这一个问题，非要走完整流程吗？**
不用。直接读 `CAPABILITIES.md` 找到对应能力（SPEC-03 + SPEC-06），把 `03-implement.md` 和那两份 SPEC 一起贴给 AI 即可。五步流程是为「系统性补齐」设计的。

**Q：我的后端是 Python / Go，前端是 Vue / Svelte，规范还适用吗？**
适用。规范本身语言无关，`ADAPTATION.md` 给了常见栈的概念映射表。唯一需要你自己判断的是**并发原语**（Effect / async-await / goroutine / asyncio）的等价写法，`ADAPTATION.md` 里有对照。

**Q：17 项全做完要多久？**
`CAPABILITIES.md` 里每项都有工作量档位。全做完是数周量级的工程，但 **P0 三项（SPEC-01/02/03）通常几天就能跑通**，而且它们单独就能解决「刷新丢过程」和「流式卡顿」两个最常见的问题。

**Q：AI 实施完了，我怎么知道它没糊弄我？**
跑 `04-verify.md`。它要求 AI 对每条断言给出**通过/失败/不适用**三选一，且通过必须附证据（测试文件路径、或可复现的操作步骤）。「不适用」必须写理由。

**Q：能不能让 AI 一次做完所有能力？**
强烈不建议。依赖关系会让它在上下文里同时维护 17 套约束，结果是每一套都做得半吊子。一次一个能力、做完验收再下一个，是这套工具包唯一推荐的节奏。

## 9. 与分析原文的关系

| | 分析原文 `../context-and-streaming/` | 本工具包 `agent-runtime-kit/` |
| --- | --- | --- |
| 回答的问题 | opencode **是怎么做的** | 你的项目**应该满足什么** |
| 形式 | 带 `path:line` 引用的技术分析 | 规范性条款 + 提示词 |
| 代码 | 大量 opencode 源码摘录 | 语言无关伪代码 + 接口契约 |
| 用途 | 理解原理、查具体实现细节 | 交给 AI 去实施和验收 |
| 依赖 | 需要 opencode 仓库在手 | **自包含，可单独复制** |

遇到「规范说要这么做，但我不理解为什么」时，去查分析原文对应章节——每份 SPEC 的头部都标了来源章节。
