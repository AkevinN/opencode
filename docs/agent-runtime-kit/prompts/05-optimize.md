# 提示词 05 · 优化（Optimize）

> **怎么用**：用于「已经有实现，但偏离规范」的情况。替代 `03-implement`。在末尾填 §8。
>
> **产出**：最小修正 diff + `optimize-SPEC-NN.md`。
>
> **本阶段的铁律：修正，不重写。** 见 §1。

---

现在优化一个**已有实现**，让它符合 SPEC-NN。

## 1. 本阶段的铁律

### 修正，不重写

你面前的代码是能跑的、被人用过的、可能承载着你不知道的历史决策。

**默认假设是「它有理由长成这样」**，不是「写得不好，我来重构」。

| 允许 | 不允许 |
| --- | --- |
| 补一个缺失的分支 | 把整个函数重写成规范里的伪代码形状 |
| 改一个判断条件 | 换掉整个模块的架构 |
| 加一层校验 | 换数据结构 |
| 补一个事务边界 | 换 ORM / 换并发原语 |
| 改一个常量 | 改文件组织 |

**如果某条必须级条款真的需要架构级改动才能满足**，不要自己动手：停下来告诉我改动面和代价，让我决定是改架构还是接受偏离。

### 每个改动必须对应一条具体的偏离

不允许「顺手改进」。每一处 diff 都要能回答：**这修的是哪条 `R-NN-MM` 的哪个偏离？**

发现了规范没覆盖的其它问题，记在报告的「规范外发现」里，**不要动手**。

## 2. 输入

1. `agent-runtime-kit/spec/SPEC-NN-*.md` —— 全文
2. `agent-runtime-kit/acceptance/SPEC-NN.yaml` —— 断言
3. `audit-report.md` 里该 SPEC 的小节（如果做过审计）
4. `verify-SPEC-NN.md`（如果做过验证，`fail` 项就是要修的清单）
5. 实际的实现代码

## 3. 流程

### 步骤 1：定位偏离

对照规范第 3 节的每一条，找出现有实现的偏离。每条偏离记成：

```markdown
**[R-NN-05]** <条款标题> · **必须**

- **规范要求**：<一句话>
- **当前实现**：`src/xxx.ts:123-135`
  ```ts
  <贴 ≤8 行的关键代码>
  ```
- **偏离点**：<具体差在哪>
- **实际后果**：<会在什么场景下出什么问题。要具体，不要说「可能有隐患」>
- **修正规模**：一行 / 一个分支 / 一个函数 / 架构级
```

**按「实际后果的严重度 × 修正规模的小」排序输出。** 一行能修好的高危偏离排最前。

### 步骤 2：分类并等我确认

把偏离分三类：

| 类 | 判据 | 处理 |
| --- | --- | --- |
| **A · 立刻修** | 必须级 + 修正规模 ≤ 一个函数 | 直接做 |
| **B · 需要决策** | 必须级 + 架构级改动，或应该级 + 修正规模大 | 列出代价，等我拍板 |
| **C · 记录不动** | 可以级，或有明确的项目特定理由偏离 | 只记录 |

输出分类结果，**等我确认再动手**。

### 步骤 3：逐条修正

一次修一条偏离，每条：

1. 改动**尽可能小**——优先改条件、加分支、补校验，而不是重写。
2. 保持周围代码的风格，不要引入新的写法。
3. 在改动处加一行注释说明条款号和它防的是什么：
   ```ts
   // R-14-10: baselineSeq 取压缩消息的 seq 而非 latestSequence，
   // 否则压缩点之后的 system 消息会被水位线误杀
   ```
4. **每条修完确认现有测试没被破坏**，再修下一条。

### 步骤 4：补测试

对每条修正的偏离，找到 `acceptance/SPEC-NN.yaml` 里对应的断言，补一个测试。

**测试必须在修正之前是红的。** 做法：写完测试先 revert 修正，确认测试变红，再恢复。在报告里写明你做了这个验证。

没做这一步的测试没有价值——它可能在修正前就是绿的。

### 步骤 5：交付

```markdown
## SPEC-NN 优化完成

### 修正清单
| # | 条款 | 偏离 | 改动 | 文件 |
| --- | --- | --- | --- | --- |
| 1 | R-14-10 | 用 latestSequence 而非 compaction.seq | 改一行 | `src/compact.ts:88` |

**改动统计**：N 个文件，+N/-N 行

### 每条修正的验证
| 条款 | 断言 | 测试 | 修正前是否红 |
| --- | --- | --- | --- |
| R-14-10 | A-14-10 | `test/compact.test.ts:34` | ✅ 确认过 |

### 需要你决策的（B 类）
| 条款 | 偏离 | 修正方案 | 改动面 | 代价 | 我的推荐 |
| --- | --- | --- | --- | --- | --- |

### 保留的偏离（C 类）
| 条款 | 等级 | 为什么保留 |
| --- | --- | --- |

### 规范外发现
<与规范无关但你在过程中注意到的问题。只描述，不动手。没有就写「无」>

### 回归风险
<这次改动可能影响到的其它行为，以及你怎么确认它们没坏>
```

## 4. 常见的"优化"陷阱

| 陷阱 | 为什么错 |
| --- | --- |
| 「顺手把这个函数拆成三个」 | 拆分本身不修任何偏离，但引入回归风险 |
| 「这里应该用 async iterator」 | 风格偏好不是规范要求 |
| 「把这些常量提取出来」 | 除非规范要求参数可配置，否则不动 |
| 「加个类型更严格的 schema」 | 除非规范要求，且注意 SPEC-16 R-16-20：有些地方**故意**用宽松类型 |
| 「补充错误处理」 | 除非对应某条条款。乱补会改变失败语义 |
| 「顺便把这个 bug 也修了」 | 它不在本次范围。记在「规范外发现」里 |
| 「规范说要这样，我全按规范重写一遍」 | 规范约束**行为**，不约束**代码形状** |

## 5. 判断「是否真的偏离」

在把某处标成偏离之前，先确认：

1. **行为是否真的不同？** 写法不同不等于行为不同。规范的伪代码是**一种**表达，不是唯一正确的形状。
2. **是不是在别的地方已经处理了？** 比如规范要求的校验可能在调用方做了。**先追一遍调用链**。
3. **是不是项目有意为之？** 看注释、看 git blame、看 `CONTRIBUTING.md`。有明确理由的偏离归入 C 类。

**把没有偏离的地方标成偏离，然后"修正"它，是本阶段最容易造成回归的方式。**

## 6. 绝对不要做的事

- ❌ 不要在没输出偏离清单、没等我确认分类的情况下就开始改
- ❌ 不要做架构级改动而不先问我
- ❌ 不要重写能跑的函数
- ❌ 不要在同一次改动里混入规范外的修改
- ❌ 不要补一个"修正前就是绿的"的测试
- ❌ 不要改格式化、lint 配置、依赖版本
- ❌ 不要把「代码风格与规范示例不同」当成偏离

## 7. 质量自检

- [ ] 每一处 diff 都能指向一条具体条款
- [ ] 每条修正都有对应断言的测试，且确认过修正前是红的
- [ ] 没有做任何架构级改动（或做了但先得到了我的批准）
- [ ] 现有测试全部仍然通过
- [ ] 「规范外发现」里的东西一个都没动
- [ ] 改动统计的行数与实际 diff 一致
- [ ] 重新跑了一遍 `04-verify` 覆盖的断言，之前 `fail` 的现在 `pass`
