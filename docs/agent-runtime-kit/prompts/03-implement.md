# 提示词 03 · 实施（Implement）

> **怎么用**：每实施**一个** SPEC 就贴一次本文件，并在末尾填上 §9 的参数。
>
> **产出**：代码改动 + `notes-SPEC-NN.md`（适配说明）。
>
> **一次只做一个 SPEC。** 同时做多个会让每一个都成为半成品。

## 2. 实施前必须做的三件事

### ① 读规范全文

读 `agent-runtime-kit/spec/SPEC-NN-*.md` 的**全部章节**，不要跳读。
重点：第 3 节（规范条款）、第 4 节（算法规范）、第 7/8 节（边界情况、反模式）。

同时读 `agent-runtime-kit/acceptance/SPEC-NN.yaml` —— 它定义了「做完之后怎么算做对了」。
**在写第一行代码之前就知道验收标准**，这会实质性改变你的实现方式。

### ② 确认依赖已满足

SPEC 头部标了依赖的 SPEC。逐个确认它们在我的项目里**已经实现且满足必须级条款**。

- 依赖未实现 → **停下来告诉我**，不要"先做个简化版凑合"。
- 依赖部分实现 → 列出缺的条款，问我是先补依赖还是接受受限实现。

**特别注意成对依赖**：SPEC-12 和 SPEC-13 必须一起实现。如果你被要求单独做其中一个，先跟我确认。

### ③ 确认适配方式

读 `ADAPTATION.md` 里对应的映射。规范里用的概念（Scope、Deferred、KeyedMutex、PubSub、Signal…）在我的技术栈里对应什么，**先说出来再动手**。

**输出方案后停下来。** 等我确认再写代码。

### 步骤 2：写代码

确认后开始实施。约束：

1. **最小 diff**。只改实现这个能力必需的地方。
2. **跟随宿主约定**。看周围代码怎么写就怎么写——命名、错误处理、日志、导出方式、注释密度。规范里的示例代码是**表达语义**用的，不是风格模板。
3. **条款号写进注释**。在关键分支上标注它满足哪条：
   ```ts
   // R-13-10: 换纪元时取压缩消息的 seq，不是当前最新 seq，
   // 否则介于压缩点和当前之间的 system 消息会被水位线误杀
   const baselineSeq = replacementSeq ?? (await latestSequence(sessionId))
   ```
   **只在"不这么写就会被改错"的地方加**，不要每行都标。
4. **边界情况按第 7 节的表逐条实现**。那张表里的每一行都是真实踩过的坑。
5. **反模式表当 checklist 用**。写完对着第 8 节过一遍。

### 步骤 3：自测

在交付前自己验证。按 `acceptance/SPEC-NN.yaml` 里 `kind` 字段分：

| kind | 怎么处理 |
| --- | --- |
| `unit` | **写成实际的测试**，用我项目的测试框架 |
| `integration` | 写成测试；确实难以自动化的，写出手动复现步骤 |
| `manual` | 写出精确的手动验证步骤（点哪里、看什么、期望值是多少） |

**测试写在我项目的测试目录里，用我项目的测试框架。** 不要自己引入新的测试工具。

## 4. 遇到冲突时怎么办

### 规范与我项目的现有架构冲突

**不要自己选一边。** 把冲突摊开给我：

```
冲突：SPEC-01 R-01-05 要求事件的 seq 全局单调，
但我们的 messages 表用的是会话内自增 id。

选项 A：加一张全局事件表，messages 表不动
  代价：多一次写入；好处：不动现有表，无迁移风险
选项 B：给 messages 加全局 seq 列 + 回填
  代价：需要迁移，停机或双写；好处：结构更简单

我推荐 A，因为你说过 messages 表结构冻结。
```

### 规范没覆盖我遇到的情况

**停下来问。** 不要臆测。问的时候给出你的判断和理由，让我做选择题而不是问答题。

### 规范要求的东西在我的语言/框架里做不到

先查 `ADAPTATION.md` 的「如果我没有 X」表。还是做不到就告诉我，并说明：
- 规范为什么要这个（它防的是什么问题）
- 在我的栈里最接近的替代是什么
- 替代方案会失去哪些保证

## 5. 绝对不要做的事

- ❌ 不要在没出设计方案、没等我确认的情况下直接写代码
- ❌ 不要顺手重构无关代码
- ❌ 不要"顺便"实现别的 SPEC
- ❌ 不要加依赖不问
- ❌ 不要改格式化配置、lint 规则、tsconfig
- ❌ 不要照抄规范里的示例代码风格
- ❌ 不要跳过第 7 节的边界情况表——那些不是"nice to have"
- ❌ 不要为了让断言通过而在测试里写假的通过
- ❌ 不要在交付说明里把「未实现」写成「已实现」。漏了就说漏了

## 6. 质量自检（交付前必过）

- [ ] 设计方案得到了确认才动的手
- [ ] 每条**必须**级条款要么已实现，要么在交付说明里明确标了未实现 + 理由
- [ ] 第 7 节边界情况表的每一行都有对应处理（或明确说明为什么不需要）
- [ ] 第 8 节反模式表逐条对照过，一条都没踩
- [ ] 新代码风格与周围代码一致
- [ ] 没有引入未经批准的依赖
- [ ] `unit` 类断言都有真实测试，且测试**确实会在行为错误时失败**（改坏一行验证一下）
- [ ] 改动能编译/能跑，现有测试没被破坏

## 7. 分级实现的态度

每份 SPEC 第 9 节都给了「最小可用版」和「完整版」。

- **默认做完整版**，除非我在 §9 里说了做最小版。
- 做最小版时，**「绝对不能砍」那一段里的东西一条都不能砍**。砍了就不是这个能力的最小版，是一个不工作的仿制品。
- 砍掉的部分要在交付说明的「已知限制」里逐条列出。

## 8. 关于可调参数

SPEC 第 5 节的参数表：

- 直接用参考默认值，**除非** `02-plan` 的参数建议里对这个参数有不同意见。
- 把参数做成**可配置的常量**（放在配置文件或常量模块里），不要硬编码在逻辑中间。
- 在常量定义处写一行注释说明它的作用和调整影响。
