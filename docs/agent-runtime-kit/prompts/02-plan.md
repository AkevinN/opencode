# 提示词 02 · 计划（Plan）

> **怎么用**：在 `01-audit`（路线 B）或 `00-orchestrator`（路线 A）之后。把本文件全文贴给 AI。
>
> **产出**：`implementation-plan.md` —— 一份带里程碑、进入/退出条件、依赖顺序的实施计划。
>
> **本阶段不写代码。**

---

现在把「差距」变成「计划」。

## 1. 输入

按路线不同：

| 路线 | 你需要读的 |
| --- | --- |
| A（全新实现） | 项目画像（`00-orchestrator` 的产出）+ `CAPABILITIES.md` |
| B（审计优化） | `audit.json` + `audit-report.md` + `CAPABILITIES.md` |

**不要读 `spec/` 下的文件。** 计划阶段只需要知道「做什么、什么顺序、多大量」，不需要知道「怎么做」。规范在 `03-implement` 阶段按需读。

## 2. 先问我这五个问题

在动手排计划之前，**必须**先问清楚。这些答案会实质性改变计划形状：

1. **时间预算**：这轮要做多久？（几天 / 两三周 / 持续迭代）
2. **痛点排序**：如果只能解决一个问题，是哪个？
3. **不能动的地方**：有没有不能改的表结构、不能加的依赖、不能破坏的对外 API、正在并行开发的模块？
4. **上线节奏**：每个能力做完就能发，还是要攒一批一起发？（影响能不能拆成小步）
5. **谁来验收**：你自己跑测试，还是要我写自动化测试？

**问完等我回答再继续。** 不要自己假设答案。

## 3. 排序规则（按优先级，冲突时上面的赢）

1. **依赖图优先。** `CAPABILITIES.md` 的依赖关系是硬约束。被依赖的能力必须先做。
   - 特别注意：**SPEC-12 和 SPEC-13 必须一起做**。只做 12 不做 13，你得到一堆能算出变化的来源但无处安放；只做 13 不做 12，纪元里装的还是拼接字符串，没有意义。
   - **SPEC-01 是几乎所有后端能力的地基**，它没做好，后面全是空中楼阁。
2. **阻塞点优先。** `audit.json` 的 `blocking` 数组里出现频率最高的，先做。
3. **用户痛点优先。** 我在 §2 问题 2 里说的那个。
4. **小步优先。** 同等条件下，先做工作量 S 的，尽早产生可见成果。
5. **风险后置。** 需要改表结构、需要数据迁移的，排在同层能力的最后。

## 4. 里程碑的划分规则

**一个里程碑 = 一组能一起验收、一起上线的能力。**

划分约束：

- 每个里程碑**最多 3 个 SPEC**。超过 3 个，验收时你分不清是哪个改动引入的问题。
- 每个里程碑结束时，项目**必须是可运行、可发布的状态**。不允许「这个里程碑做一半，下个里程碑接上」。
- 有依赖关系的能力可以放同一个里程碑（如 SPEC-12+13），但**不能跨里程碑拆开一个能力**。
- 需要数据迁移的能力**单独一个里程碑**。

每个里程碑必须写清：

```markdown
### 里程碑 M1 · <名字>

**包含**：SPEC-01（消息模型）、SPEC-02（事件与传输）
**预计工作量**：<档位，参考 CAPABILITIES.md>
**解决的痛点**：<对应我在 §2 里说的哪个>

**进入条件**：
- [ ] <开始前必须成立的事。例：确认 messages 表可以加列>

**退出条件**（= 验收标准）：
- [ ] `acceptance/SPEC-01.yaml` 的必须级断言全部通过
- [ ] `acceptance/SPEC-02.yaml` 的必须级断言全部通过
- [ ] <本里程碑特有的、可观察的结果。例：刷新页面后进行中的回答能完整恢复>

**主要改动面**：
| 文件/模块 | 改动类型 | 风险 |
| --- | --- | --- |
| `src/session/message.ts` | 新增 seq 字段 | 需要迁移，旧数据回填 |

**回滚方案**：<出问题怎么退回去>

**需要我决策的点**：
1. <列出需要我拍板的选择，每个都给你的推荐和理由>
```

## 5. 可调参数的处理

每个里程碑涉及的 SPEC，第 5 节都有「可配置参数」表。在计划里：

- **不要**逐个参数问我。
- **要**列出该里程碑里「默认值可能不适合我的项目」的参数（≤3 个），给出你的建议值和理由。

判断「可能不适合」的依据：我的项目画像里的规模、语种、部署形态。
例：「我们主要服务中文用户 → SPEC-14 的 `chars/4` 估算会低估，建议 `buffer` 从 20k 提到 30k」。

**本轮做**：SPEC-01, SPEC-02, SPEC-03, SPEC-11
**本轮不做**：<列出并说明为什么。「暂时不需要」也是合法理由，但要写出来>

## 三、依赖顺序

<mermaid 图，只画本轮涉及的能力>

<§4 格式的各个里程碑>

| SPEC | 参数 | 默认值 | 建议值 | 理由 |

## 7. 你不该做的事

- ❌ 不要读 `spec/` 下的文件（计划阶段不需要）
- ❌ 不要写代码、不要写伪代码
- ❌ 不要把 17 项全排进计划——除非我明确要求
- ❌ 不要把一个里程碑排到 3 个以上 SPEC
- ❌ 不要在没问 §2 五个问题的情况下直接输出计划
- ❌ 不要用「第一周/第二周」这种日期排期。我要的是**依赖顺序和里程碑**，具体日期由我安排
