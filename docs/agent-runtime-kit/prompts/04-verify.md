# 提示词 04 · 验证（Verify）

> **怎么用**：每实施完一个 SPEC 就贴一次本文件，在末尾填 §8。
>
> **产出**：`verify-SPEC-NN.md` + 更新后的 `acceptance/SPEC-NN.yaml`（把 `status` 填上）。
>
> **本阶段的铁律：不准改实现代码。** 见 §1。

---

现在验证 SPEC-NN 的实施结果。

## 1. 本阶段的铁律

### ❌ 不准改实现代码

验证阶段唯一允许改的是**测试文件**和**验证报告**。

**为什么**：一边验一边改，你会不自觉地把"改到能过"当成"验证通过"。发现问题就如实记下来，修复是下一轮 `03-implement` 或 `05-optimize` 的事。

例外：发现测试本身写错了（断言写反、用错 API），可以修测试。修的时候要在报告里说明。

### ❌ 不准为了通过而放宽标准

断言写的是什么就验什么。觉得某条断言不合理，**如实记为失败**并在报告里说明你的异议，不要自己改断言的含义。

### ❌ 不准编造证据

- 「测试通过」必须有实际跑过的输出。
- 「手动验证通过」必须写出你**实际执行**的步骤和**实际看到**的结果。
- 没条件跑就标 `blocked`，不要标 `pass`。

## 2. 验证输入

1. `agent-runtime-kit/acceptance/SPEC-NN.yaml` —— 断言清单
2. `agent-runtime-kit/spec/SPEC-NN-*.md` 的第 3 节 —— 断言背后的条款
3. `notes-SPEC-NN.md` —— 实施说明（尤其是「已知限制」）
4. 实际的实现代码

## 3. 逐条验证

对 YAML 里的**每一条**断言，走这个流程：

### 步骤 1：读懂断言在验什么

断言的 `statement` 是简写。看不懂就回去读它 `group` 对应的规范条款。

例：`A-13-10` 说「压缩后紧接着又产生了 2 条事件，再 prepare → baseline_seq 仍等于压缩消息 seq」
→ 它在验 R-13-10，防的是「用最新 seq 做水位线会误杀压缩点之后的 system 消息」。

### 步骤 2：按 `kind` 选验证方式

| kind | 验证方式 |
| --- | --- |
| `unit` | 跑对应的单元测试，贴出**实际输出** |
| `integration` | 跑集成测试；或按步骤手动执行并记录观察 |
| `manual` | 手动执行并记录每一步的观察结果 |

**没有对应测试的 `unit` 断言 → 现在写一个。** 这是验证阶段唯一允许新增的代码。

### 步骤 3：给判定

四选一：

| 判定 | 含义 | 证据要求 |
| --- | --- | --- |
| `pass` | 行为符合断言 | 测试文件路径 + 实际输出片段，或手动步骤 + 实际观察 |
| `fail` | 行为不符合 | **实际行为是什么** + 复现步骤 + 关联条款 |
| `n/a` | 断言前提在本项目不成立 | 说明前提为什么不成立 |
| `blocked` | 无法验证 | 说明为什么（缺环境、缺数据、需要真实 provider…） |

**`n/a` 的判定标准和审计阶段一样严格**：只有「架构上不存在那个概念」或「产品上明确不需要」才算。
「这次没实现」是 `fail`，不是 `n/a`。

### 步骤 4：对 `fail` 追根因

每条 `fail` 都要给：

```markdown
**A-NN-05** `fail`

- **断言**：<statement>
- **关联条款**：R-NN-05（必须）
- **期望**：<断言要求的行为>
- **实际**：<实际发生了什么>
- **复现**：<最小复现步骤或测试用例>
- **定位**：`src/xxx.ts:123`（如果能定位到）
- **根因判断**：漏实现 / 实现错误 / 测试写错 / 断言不适用（说明理由）
```

**不要在这里写修复方案。** 记录现象和定位就够了。

## 4. 验证的反作弊检查

对每条 `pass`，自己问一遍：

1. **这个测试真的会失败吗？** 把实现改坏一行，测试应该变红。至少对 3 条关键断言做这个"变异测试"，并在报告里写明。
2. **测试验的是断言说的那件事吗？** 别用一个更弱的条件蒙混。
   - 断言："`baseline` 与变化前**逐字节相同**" → 必须 `assert(a === b)`，不是 `assert(a.length === b.length)`
3. **手动步骤是你真的执行过的吗？** 还是你觉得"应该会这样"？

**必须对 SPEC 第 10 节点名的「必须优先验证」的那几条做变异测试。** 它们是该能力最容易做错的地方。

## 5. 报告格式

```markdown
# SPEC-NN 验证报告

验证时间：<date>
代码版本：<git rev-parse --short HEAD>
实施说明：`notes-SPEC-NN.md`

## 一、结论

**通过 / 有条件通过 / 不通过**

| 判定 | 数量 |
| --- | --- |
| pass | |
| fail | |
| n/a | |
| blocked | |

**必须级断言**：N/M 通过

> 结论判定规则：
> - 全部必须级断言 `pass` 且无 `blocked` → **通过**
> - 必须级全 `pass` 但有 `blocked` → **有条件通过**（列出待验项）
> - 有任何必须级 `fail` → **不通过**
```

## 6. 更新 YAML

验证完把结果写回 `acceptance/SPEC-NN.yaml`，只改 `status` 字段（和新增 `evidence`）：

```yaml
  - id: A-13-01
    group: "E1"
    statement: "同一会话并发调两次 `initializeEpoch` → 只产生一行"
    kind: integration
    severity: must
    status: pass                              # pending → pass/fail/na/blocked
    evidence: "test/epoch.test.ts:45"         # 新增
```

**不要改 `statement`、`kind`、`severity`、`group`。** 那些是规范的一部分。
