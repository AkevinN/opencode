# 提示词 01 · 审计（Audit）

> **怎么用**：在 `00-orchestrator` 之后使用（路线 B）。把本文件全文贴给 AI。
>
> **产出**：`audit-report.md`（人读）+ `audit.json`（机器读，供 `02-plan` 消费）。
>
> **本阶段的铁律：只诊断，不开方。** 见 §1。

---

现在做一次**现状审计**。目标是：对着 17 项能力规范，逐条判定我的项目「有没有、对不对」，并为每个判定给出**代码证据**。

## 1. 本阶段的铁律

### ❌ 不准提修改方案

不要写「建议改成…」「可以引入…」「我来帮你加…」。**一个字都不要写。**

**为什么**：审计和设计混在一起，你会一边看一边在脑子里改，然后倾向于把「我想改的地方」标成「缺失」，把「我懒得改的地方」标成「符合」。先把现状摸干净，方案是 `02-plan` 的事。

如果你在审计过程中发现了非常重要的问题，把它记在报告末尾的 **「⚠️ 审计中发现的紧急问题」** 一节，只描述现象和风险，**不写解法**。

### ❌ 不准改任何文件

本阶段唯一允许写入的文件是 `audit-report.md` 和 `audit.json`。

### ❌ 不准猜

找不到相关实现就写「未找到」，不要因为"一般项目都会有"就假定它存在。
判定为「符合」必须有能贴出来的代码位置。

## 2. 审计范围

先问我：**这次审计覆盖哪些能力？**

三个选项：

| 选项 | 覆盖 | 适合 |
| --- | --- | --- |
| **全量** | 17 项 | 想要完整的能力地图，能接受一次长会话 |
| **分层** | 只审 P0+P1（SPEC-01/02/03/04/05/06/07/08） | 大多数情况的推荐做法 |
| **定向** | 我指定的几项 | 已经知道问题在哪 |

**除非我明确说要全量，默认建议「分层」。** 一次审 17 项会让你在上下文里同时维护 344 条断言，后半程的判定质量会明显下降。

确认范围后，**每审完一个 SPEC 就输出该 SPEC 的小节，不要全部审完再一起输出**。这样我可以中途叫停或纠偏。

## 3. 每个 SPEC 的审计流程

对范围内的每一个 SPEC，按这个顺序做：

### 步骤 1：读规范

只读**这一份** `spec/SPEC-NN-*.md`，重点是第 3 节「规范条款」。
同时读 `acceptance/SPEC-NN.yaml` —— 断言告诉你「怎么观察这个行为」，比条款描述更可操作。

### 步骤 2：定位对应实现

在我的项目里找这个能力的实现。搜索策略（按有效性排序）：

1. **按概念关键词搜**：SPEC 第 2 节的类型名、字段名（如 `baseline_seq`、`compaction`、`heartbeat`）
2. **按算法特征搜**：SPEC 第 4 节伪代码里的特征操作（如 `findLast`、`realpath`、`requestAnimationFrame`）
3. **按数据结构搜**：表名、schema 定义、事件名
4. **按调用点倒推**：从 provider 调用处、HTTP 路由、前端渲染入口往回找

**找不到不等于没有**——换 2-3 组关键词再确认。但确认后就果断判「未找到」。

### 步骤 3：逐条判定

对该 SPEC 的**每一条** `R-NN-MM`，给出四选一：

| 判定 | 含义 | 证据要求 |
| --- | --- | --- |
| `满足` | 行为与条款一致 | **必须**给 `file:line`，并引用关键代码片段（≤5 行） |
| `部分满足` | 主路径对，但缺边界处理 | **必须**给 `file:line`，并说明**具体缺哪个分支** |
| `不满足` | 行为与条款冲突，或完全没有 | 给出应该在但没有的位置，或冲突的 `file:line` |
| `不适用` | 该条款的前提在本项目不成立 | **必须**说明前提为什么不成立 |

**「不适用」要谨慎。** 它的合法用法只有两种：

- 项目架构上不存在那个概念（例：没有多目录工作区 → SPEC-13 R-13-13 不适用）
- 产品上明确不需要（例：纯单用户 CLI → SPEC-02 的部分多订阅者条款不适用）

**不合法**的用法：「我们现在还没做到」（那是 `不满足`）、「这个太细了」（那是 `不满足`）。

### 步骤 4：记录风险

对每条 `不满足` / `部分满足` 的**必须**级条款，写一句**具体的失败场景**：

- ✅ 好："工具输出 200MB 的构建日志时，整个响应体进内存并写进消息表，进程 OOM"
- ❌ 差："可能有性能问题"

失败场景要能对应到 `acceptance/SPEC-NN.yaml` 里的某条断言。能对应上就写断言 id。

### 步骤 5：输出该 SPEC 的小节

```markdown
### SPEC-NN · <名称>

**总体判定**：缺失 / 部分 / 符合
**实现位置**：`src/xxx/yyy.ts`（或「未找到」）
**满足 / 部分 / 不满足 / 不适用**：3 / 5 / 6 / 1

| 条款 | 等级 | 判定 | 证据 | 备注 |
| --- | --- | --- | --- | --- |
| R-NN-01 | 必须 | 满足 | `src/a.ts:34-38` | |
| R-NN-02 | 必须 | 部分 | `src/a.ts:51` | 主路径对，但没处理 X 分支 |
| R-NN-03 | 必须 | 不满足 | — | 完全没有这个机制 |
| R-NN-04 | 应该 | 不适用 | — | 本项目无多工作区概念 |

**风险（按严重度排）**：
1. **[R-NN-03]** <具体失败场景>。对应断言 `A-NN-05`。
2. ...
```

## 4. 最终报告格式

所有 SPEC 审完后，输出 `audit-report.md`：

```markdown
# 运行时能力审计报告

生成时间：<date>
审计范围：<全量 / 分层 / 定向：SPEC-xx, SPEC-yy>
代码库版本：<git rev-parse --short HEAD>

## 一、总览

| SPEC | 能力 | 判定 | 必须条款满足率 | 实现位置 |
| --- | --- | --- | --- | --- |
| SPEC-01 | 消息模型 | 部分 | 9/16 | `src/session/` |
| ... |

**符合**：N 项　**部分**：N 项　**缺失**：N 项　**不适用**：N 项

## 二、按严重度排序的风险清单

> 排序依据：①能力是否被其它能力依赖（见 CAPABILITIES.md 依赖图）②失败场景的影响面 ③触发概率

| # | 条款 | 能力 | 失败场景 | 影响面 |
| --- | --- | --- | --- | --- |
| 1 | R-02-04 | 事件传输 | ... | 所有会话 |

## 三、逐 SPEC 明细

<上面步骤 5 的各个小节>

## 四、依赖图上的阻塞点

<哪些缺失的能力正在阻塞其它能力。例：SPEC-01 的 seq 缺失导致 SPEC-13/14 都无法实现>

## 五、⚠️ 审计中发现的紧急问题

<与规范无关但严重的问题。只描述现象和风险，不写解法。没有就写「无」>

## 六、审计盲区

<你没能确认的地方，以及为什么。例：「SPEC-04 的滚动行为需要运行时观察，静态代码无法判定 R-04-09」>
```

同时输出 `audit.json`（供 `02-plan` 消费）：

```json
{
  "generated_at": "2026-01-01T00:00:00Z",
  "scope": ["SPEC-01", "SPEC-02"],
  "repo_rev": "abc1234",
  "specs": [
    {
      "id": "SPEC-01",
      "verdict": "partial",
      "location": "src/session/",
      "must_total": 12,
      "must_satisfied": 9,
      "clauses": [
        { "id": "R-01-01", "level": "must", "verdict": "satisfied",
          "evidence": "src/session/message.ts:34-38", "note": "" },
        { "id": "R-01-03", "level": "must", "verdict": "unsatisfied",
          "evidence": null, "note": "无事件表",
          "failure": "刷新页面后进行中的回答丢失", "assertion": "A-01-07" }
      ]
    }
  ],
  "blocking": [
    { "spec": "SPEC-01", "blocks": ["SPEC-13", "SPEC-14"], "reason": "缺少全局单调 seq" }
  ]
}
```

`verdict` 的取值：`satisfied` / `partial` / `unsatisfied` / `not_applicable`。
SPEC 级 `verdict` 的取值：`compliant` / `partial` / `missing`。

## 5. 审计质量自检

交报告前，自己过一遍：

- [ ] 每条「满足」都有 `file:line`，不是「在 xxx 模块里」这种模糊指代
- [ ] 每条「不适用」都写了前提为什么不成立
- [ ] 每条「不满足」的必须级条款都有具体失败场景，不是「可能有问题」
- [ ] 报告里**没有任何**「建议」「应该改成」「可以引入」
- [ ] `audit.json` 能被 JSON 解析
- [ ] 「审计盲区」一节不是空的——静态审计必然有看不到的东西，一条都没有说明你没认真想
